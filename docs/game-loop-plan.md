# Полный план работ: экстракция, дом, арена

Составлено 17.08.2026. Все решения приняты владельцем в диалоге и зафиксированы ниже. Теория —
[game-loop.md](game-loop.md). Кода ещё нет, это план для продолжения на другой машине.

Оба репозитория: клиент `advenjohub5.5`, сервер `game-server`. Правила работы — см.
[progression-handoff.md](progression-handoff.md): комментариев в коде нет, кроме строки с путём файла;
коммиты и пуши делает владелец; сервер и браузер он запускает сам.

## 2. Блок A — боевой режим

Фундамент для трёх запретов. Делать первым.

**Сервер.** Поле `player.combatUntil = 0` рядом с `player.canyon` (создание игрока, ~5715). Функция
`markInCombat(player)` ставит `Date.now() + COMBAT_MODE_MS` (10 000). Вызывается из двух конвейеров урона,
вынесенных на уровень модуля в Фазе 4: `applyPlayerDamage` (цель и, если атакующий — игрок, атакующий) и
`applyEnemyDamage` (игрок-атакующий). Через них уже проходят способности, зоны, DoT и обычные выстрелы —
одна точка ловит всё.

Сообщение `combatState { until }` шлём **только на переходе** из мира в бой и не чаще раза в 2 секунды при
продлении. Клиент дальше сам считает обратный отсчёт.

Проверяют флаг: `homeTeleport`, `stuckTeleport`, покупка страховки в `handleShopBuyItem`.

**Клиент.** `NetworkManager.onCombatState` → `useHudState` → индикатор в `HUD.tsx`; в `SettingsWindow.tsx`
кнопка «I'm Stuck» неактивна с подписью причины.

**Риски.** Стоя в чужой зоне замедления с DoT игрок не выходит из боя никогда — это задумано, но проверить,
что зона, которую поставил он сам, его в бой не вводит. Второе: `applyPlayerDamage` вызывается и при уроне
в 0 (поглощён щитом) — в бой вводить всё равно нужно, иначе щит становится способом выйти из боя.

## 3. Блок B — «I'm Stuck» на сервере

Сейчас кнопка чисто клиентская (`GameLocationOrchestration.teleportToSafeZone` зовёт
`changeLocation('main-world')`), сервер видит обычную смену локации. После введения потери лута это главный
эксплойт, поэтому блок идёт вторым.

**Сервер.** Сообщение `stuckTeleport`, свой rate limit. Кулдаун 1 час в `progress.data.stuckUsedAt`.
Логика:

- в боевом режиме — отказ `in_combat`;
- в сегменте каньона — **смерть**: ящик падает, идёт обычный экран смерти, кулдаун всё равно тратится;
- иначе — принудительный телепорт в безопасную зону main-world через `spawnInSafeZone` +
  `notifyLocationTransition`, `grantSpawnProtection`.

Ответ `stuckResult { ok, reason, cooldownUntil }`.

**Клиент.** `teleportToSafeZone` больше не меняет локацию сам, а шлёт сообщение. Приход новой позиции
обрабатывается как респавн — переиспользуем путь `onRespawn` в `GameNetworkHandlers.ts:461`, но телепорт
должен ставить игрока в `data.position`, а не в `getSpawnPoint()` локации.

## 4. Блок C — дом

### C1. Лоты в магазине

Три новых товара в **трёх** местах: `src/core/lib/shopCatalog.ts` (сайт, цены и админка),
`src/features/game/data/placeableItems.ts` (список в окне магазина — `ShopWindow` рисует именно его),
`SHOP_ITEMS` в `server.js:2764` (валидация покупки).

| id | Цена | maxOwned | Что делает |
|---|---|---|---|
| `home-teleport` | 250 Ash | 10 | расходник, телепорт домой |
| `storage-crate` | 200 Ash | без лимита | право поставить ящик в комнате |
| `run-insurance` | 1000 Ash | 1 | страховка на одну смерть |

Все три не ставятся в мире, поэтому `placementScope` у них нет, а `placeable: false`. Счётчик живёт в
`player.placeables` и уже персистится — отдельных полей не нужно.

### C2. Маяк спавна и ящики как постройки

`BuildCatalog.ts` — две новые записи, `slot: "object"`, `blocking: true`:

- `spawn-beacon` — светящийся столб с кристаллом, ровно один на участок;
- `storage-crate` — сундук, количество ограничено купленным.

`BuildRenderer.ts` — регистрация интеракций по образцу постеров (`PAINT_PREFIX`, строка 170): маяку
`interactionId = "spawn-beacon"`, ящику `storage:<pieceKey>`. `InteractionSystem.ts` — две новые ветки в
цепочке `id === ...` (строки 113–189).

`BuildEditor` / `BuildSession` — лимиты в редакторе: второй маяк не ставится, ящиков не больше купленных,
**непустой ящик не сносится** (кнопка стирания заблокирована с подсказкой).

`app/api/game/room-layout/route.ts` — те же лимиты в `layoutSchema` при сохранении, потому что редактор
можно обойти запросом.

### C3. Как сервер узнаёт координаты

**Важное архитектурное решение.** Сервер не читает `room_layouts` и не пишет в `game_progress.data` с сайта.
Вместо этого `player-status` (уже опрашивается раз в 8 секунд) дополнительно отдаёт по каждому игроку:

```
homeSpawn: { x, y, z } | null
storages: [{ key, x, y, z }]
```

Роут считает их из `room_layouts` на лету: находит пьесы `spawn-beacon` / `storage-crate` и переводит
клетки в мир через `cellToWorld` из `BuildLayout.ts` (чистый TS, импортируется в роут).

**Почему так.** Если бы сайт при сохранении комнаты писал координаты в `game_progress.data`, он бы
конкурировал с игровым сервером, который периодически сохраняет свою копию того же JSON целиком. Игрок
почти всегда онлайн, когда строит, — его сохранение затёрло бы запись сайта. Вычисление на чтении убирает
гонку полностью.

### C4. Экран смерти

`respawnRequest` получает поле `target`: `hall` | `home` | `canyon_hub`. Сервер валидирует (дом — только
если маяк есть, хаб — только если смерть случилась в сегменте) и при мусоре откатывается на `hall`.
`DeathScreen.tsx` из надписи «Press SPACE» превращается в три кнопки; таймера нет, экран висит до выбора.

### C5. Телепорт домой

Сообщение `homeTeleport`. Проверки по порядку: жив, не в бою, не в сегменте каньона, кулдаун вышел, заряд
есть. Дальше `player.homeTeleportCastUntil = now + 5000`, ответ `homeTeleportResult { casting: true }`.
Завершение — в существующем тике `abilityTick` (200 мс). Любой вызов `applyPlayerDamage` по игроку сбрасывает
каст и шлёт `homeTeleportResult { cancelled: true }`.

Заряд списывается **в момент успешного завершения**, не на старте.

### C6. Хранилище

Содержимое — `progress.data.storage`, объект вида `{ "<pieceKey>": [ { address, name, symbol, image, quantity } ] }`,
до 50 позиций на ящик. Сообщения `storageOpen`, `storageDeposit`, `storageWithdraw`; проверки: локация —
собственная комната, расстояние до ящика ≤ 4, ключ ящика есть в `storages` из `player-status`.

Доступ только владельцу комнаты (`player.userId` против id из `player-room-<uuid>`), а не по правам
редактирования: гость в открытой комнате не должен видеть чужие токены.

Новое окно `ui/StorageWindow.tsx` — две сетки, инвентарь и ящик, перенос стеками. Переиспользовать сетку
из `InventoryGrid.tsx`.

**Риск: осиротевшее содержимое.** Ящик снесли, а токены в нём остались — например, потому что редактор
открыт со старым состоянием или сохранение прошло раньше, чем сервер записал депозит. Защита в два слоя:
редактор не даёт стереть непустой ящик, а сервер при исчезновении ключа из `storages` не удаляет данные,
а перекладывает их в `progress.data.storageOrphan` и при появлении нового ящика доливает в него, уведомляя
игрока. Молча терять токены нельзя ни при каком раскладе.

## 5. Блок D — ящик смерти

**Сервер.** В `markPlayerDead` после отметки смерти:

1. если `placeables['run-insurance'] > 0` — списать заряд, ящик не создавать, отправить
   `insuranceConsumed`; инвентарь остаётся целиком;
2. иначе, если локация не арена и инвентарь не пуст — `spawnDeathCrate(player, position)`.

`spawnDeathCrate` переносит **весь** `player.inventory` в запись `lootDrops` вида
`{ kind: 'crate', locationId, instance, segment, entries, ownerId: null, createdAt }` и очищает инвентарь.

**Ящик хранит стеки, а не плоский список.** Текущий лут — массив одиночных токенов; инвентарь на 200 позиций
по 50 штук превратился бы в 10 000 элементов. Поэтому у ящика своё поле `entries` с `quantity` и свои
сообщения `crateSpawn` / `crateDespawn` / `crateLoot`, а не переиспользование `lootSpawn`.

Доработки существующей машинерии:

- рассылка `dropLoot` и сборщика мусора жёстко идёт в `main-world` — ящику нужен `broadcastToLocation` по
  фактической локации, а в каньоне — только владельцу;
- `handleLootPickup` пускает только в `main-world` и `tower-first-floor` — для ящиков добавить `cave`;
- `clearCanyonLoot` и `preparePlayerEnemiesForSegment` **не трогают ящики** — иначе забег за телом
  невозможен;
- в `ws.on('close')`: если игрок в боевом режиме или в сегменте каньона — создать ящик **до**
  `persistPlayer`, иначе токены сохранятся в базу и дублируются.

Подбор `crateLoot`: проверки локации, инстанса, расстояния ≤ 3; в каньоне — только владелец. Перенос стеков
с учётом потолка в 200 позиций (`addTokensToInventory`, ~3043) — что не влезло, остаётся в ящике.

**Клиент.** Новая сущность `entities/DeathCrate.ts` (сундук с крышкой и свечением), обработка в
`systems/LootSystem.ts`, интеракция по `E` через `InteractionSystem` с id `death-crate:<id>` — в отличие от
обычного лута, который подбирается автоматически при подходе.

**Риски.**

- Два игрока жмут `E` одновременно. Узел один и однопоточный, но между проверкой и мутацией не должно быть
  ни одного `await` — иначе оба заберут. Удалять/уменьшать запись синхронно, `persistPlayer` только после.
- Смерть в личной комнате: дом обычная зона, ящик упадёт там и его заберёт тот, кого хозяин впустил. Это
  следствие решения 16, а не баг.
- Ящик в каньоне живёт 5 минут и виден только владельцу; при выходе из локации инстанс исчезает вместе с
  ящиком. Отдельно уведомить игрока текстом, иначе он решит, что потерял вещи из-за бага.
- Смерть с пустым инвентарём не должна плодить пустые ящики.

## 6. Блок E — страховка

Покупка — обычный `shopBuyItem` с двумя дополнительными проверками: не в бою и `maxOwned` = 1. Списание —
в `markPlayerDead` первым шагом. Индикатор — в `Inventory.tsx` и маленькой иконкой в `HUD.tsx`.

Сообщение при срабатывании обязательно: «Insurance paid out — your tokens are safe». Без него игрок решит,
что механика не работает, и перестанет покупать.

## 7. Блок F — каньон

**Площадка эвакуации.** `SegmentBuilderSystem.buildReturnTeleporter(content, startZ + 15)` (вызов на
строке 64) переезжает в зону босса: `startZ + SAFE_ENTRANCE_DEPTH + COMBAT_DEPTH + 20`. Площадка строится
погашенной, зажигается по приходу `canyonCleared`. Нужен метод `setActive(boolean)` у построенной группы.

**Серверная проверка.** `handleCanyonReturnToHub` (сейчас без единой проверки) требует:
`player.canyon.runCleared === true` и расстояние до площадки ≤ 5. Флаг `runCleared` ставится при смерти
босса сегмента и сбрасывается в `preparePlayerEnemiesForSegment`.

**Лут за повтор.** В `handleEnemyDeath` условие `if (!alreadyCleared)` убирается, вместо него множитель
`alreadyCleared ? 0.3 : 1` на `lootMin`/`lootMax`. Округление вниз, но не ниже нуля: слабые мобы на повторе
иногда не дадут ничего, и это нормально.

**Забег за телом.** Работает так: смерть → экран смерти → Canyon Hub → варп в тот же сегмент (уже открыт,
`handleCanyonWarp` пускает в любой ≤ `maxSegmentReached`) → игрок появляется у входа сегмента → бежит к
ящику. Мобы и босс уже респавнулись. Пять минут на 100–460 метров — успеть можно, если не отвлекаться.

**Риски.**

- Ящик лежит в сегменте, игрок варпается в **другой** сегмент — ящик не должен ему рисоваться. У записи
  есть `segment`, фильтровать по нему при отправке и при подборе.
- Игрок умер, вышел из игры, зашёл снова — `player.canyon` пересоздаётся, ящик потерян. Ожидаемо, но в
  сообщении о смерти это надо проговорить.
- После переноса площадки старый порог в следующий сегмент и новая площадка стоят рядом. Проверить, что
  игрок не проваливается в следующий сегмент, целясь в площадку.

## 8. Блок G — группы

Первая система групп в игре, нужна для арены и позже для кооп-каньона и рейда в пещере.

**Сервер, новый модуль `game-server/party.js`** (по образцу `abilities.js`): `createParty`, `invite`,
`accept`, `decline`, `leave`, `kick`, `disband`, максимум 4, передача лидерства при выходе лидера. Состояние
только в памяти, в базу не пишем — партия живёт сессию.

Сообщения: `partyInvite`, `partyAccept`, `partyDecline`, `partyLeave`, `partyKick` → ответы `partyState`
(состав, лидер), `partyInviteReceived`, `partyDisbanded`.

**Клиент.** `ui/PartyPanel.tsx` внутри `SocialWindow`, рамки участников в `HUD.tsx`, всплывающее
приглашение — по образцу `TradeInvitePopup.tsx`.

**Риски.** Приглашение игроку, который вышел; двойное принятие двух приглашений; лидер вышел из игры во
время забега арены. Все три решаются одним правилом: партия проверяется на живость при каждом действии, а
арена привязана к id забега, а не к партии — распад партии посреди забега его не отменяет.

## 9. Блок H — арена в Events Hall

**Сервер, новый модуль `game-server/arena.js`.** Состояние забега: `runId`, участники, номер волны, HP
свечи, живые мобы, фаза (`prep` / `wave` / `pause` / `over`), накопленные Ash и XP по игрокам.

- Изоляция забегов — через существующее поле `instance` в локации `tower-events`.
- Волны: мобы берутся из `ENEMY_TYPES` по биомам каньона, чем дальше волна — тем злее тип. Каждая 5-я —
  босс биома. Количество и множители здоровья считаются от номера волны, потолок одновременных мобов ~30.
- Пауза между волнами 15 секунд — окно для подъёма павших.
- Подъём: `arenaRevive { targetId }`, канал 3 секунды, только в фазе `pause`.
- Свеча — цель с HP: мобы, не видящие живого игрока, идут к ней и бьют её. **Это единственное место, где
  придётся тронуть ИИ врагов** — сейчас цель всегда игрок, а скорость и атаки правятся в пяти местах
  движения (см. progression-handoff, Фаза 4).
- Конец забега: HP свечи ≤ 0 или все участники выбыли. Начисление Ash (25 × номер волны, потолок 1500) и
  XP (предложение: 50 × номер волны, потолок 3000 за забег) — **на сервере, разом в конце**, не по ходу.
- Кулдаун на игрока — предложение 1 час, в `progress.data.arenaCooldownUntil`. Лучший результат —
  `progress.data.arenaBestWave`.
- Лут не выпадает: арена добавляется в исключения `spawnDeathCrate`.

**Клиент.** `EventsHall.ts` — свеча в центре (растёт с волной, краснеет от урона), ворота спавна по краям,
терминал старта. Новые `ui/ArenaPanel.tsx` (сбор группы, старт, правила) и `ui/ArenaHUD.tsx` (волна, HP
свечи, таймер паузы, состояние участников). Мобов рисует существующий `EnemySystem` — он уже умеет
`enemyState` для каньона, пещеры и мира.

**Риски и нагрузка.**

- 4 игрока и до 30 мобов в одном инстансе на общем тике. Каньон уже держит 10–16 мобов на игрока, но там
  они не пересекаются между игроками. Нужен потолок одновременных мобов и проверка на живых людях.
- Мобы, бьющие свечу, не должны застревать в геометрии зала — у арены нет навигации, только прямое
  движение и обход по углам, как в пещере (`CAVE_STEER_ANGLES`).
- XP на арене — новый крупный источник. При потолке 3000 за забег и кулдауне в час это ~72k XP в сутки при
  идеальной игре, то есть 5% кривой до 50 уровня. Проверить `balance:report` после включения.
- Начисление разом в конце означает, что при падении сервера посреди забега награда теряется целиком.
  Для бесплатного ивента приемлемо; для платного за TNJ — нет, там понадобится идемпотентный расчёт.

## 15. Что проверять в игре

От дешёвого к дорогому, по образцу чеклиста из progression-handoff.

1. Получил урон — индикатор боя горит 10 секунд, обе кнопки заблокированы; ударил моба — счётчик обновился.
2. «I'm Stuck» вне боя телепортирует и уходит в час кулдауна, который переживает перезаход.
3. «I'm Stuck» в сегменте каньона убивает и роняет ящик.
4. Телепорт домой: 5 секунд каста, выстрел в упор прерывает, заряд не списался.
5. Маяк поставлен → на экране смерти появилась кнопка Home → возрождение ровно у маяка.
6. Маяк переставлен → новая точка работает в течение 8 секунд без перезахода.
7. Ящик хранилища: положил, вышел из игры, вернулся — токены на месте. Гость в открытой комнате ящик не открывает.
8. Смерть в main-world: ящик виден всем, чужой игрок забирает.
9. Смерть со страховкой: ящика нет, инвентарь цел, пришло сообщение.
10. Смерть в каньоне: варп в тот же сегмент, мобы и босс на месте, ящик на месте, 5 минут тикают.
11. Разрыв связи в бою: ящик упал, при следующем входе инвентарь пуст.
12. Выход из сегмента без босса невозможен ни площадкой, ни телепортом, ни кнопкой.
13. Повторная зачистка даёт примерно треть лута.
14. Арена: группа из двух, свеча теряет HP, павшего поднимают в паузе, награда пришла один раз в конце.
15. Арена: лут при смерти не выпадает.

В консоли сервера при всех пунктах не должно быть строк `[!] ... hack:` — они означают, что античит режет
легальное действие.

### Что сделано по чеклисту

Пункты 1–6 Фазы 1 закрыты, плюс пункт 21 из Фазы 4 (площадка эвакуации) — его пришлось делать сразу,
см. «Отступления».

**Боевой режим.** `COMBAT_MODE_MS` 10 000, `COMBAT_STATE_THROTTLE_MS` 2000. `player.combatUntil` и
`player.combatStateSentAt` рядом с `lastDamageTime`. `markInCombat` / `isInCombat` / `clearCombat` стоят
возле `grantSpawnProtection`. Вызовы:

- `applyEnemyDamage` — атакующий игрок, сразу после проверки живости цели;
- `applyPlayerDamage` — атакующий (до проверок спавн-защиты и i-frames, чтобы бой засчитался даже по
  неуязвимой цели) и сама цель (после них). Урон, полностью съеденный щитом, в бой вводит: `markInCombat`
  стоит выше расчёта поглощения.

`clearCombat` вызывается в `markPlayerDead`. Сообщение `combatState { until }` шлётся на входе в бой и не
чаще раза в 2 секунды при продлении, обратный отсчёт клиент ведёт сам.

**«I'm Stuck».** Сообщение `stuckTeleport`, лимит `stuckRateLimit` 2/с. Кулдаун `STUCK_COOLDOWN_MS` час,
живёт в `progress.data.stuckUsedAt`, читается при авторизации. Порядок проверок: жив → кулдаун → бой.
В сегменте каньона — `markPlayerDead(player, 'bail-out', ...)`, кулдаун тратится. Иначе — выход в
`main-world`. Ответ `stuckResult { ok, reason, cooldownUntil, locationId }`.

Кулдаун приезжает клиенту сразу после входа: в `auth_success` добавлено поле `stuckCooldownUntil`, клиент
превращает его в `stuckResult` с `reason: 'state'` — этот повод обрабатывается молча, без уведомления.
Без этого кнопка выглядела бы доступной до первого нажатия.

**Каньон.** `handleCanyonReturnToHub` требует `player.canyon.runCleared === true` и расстояние до площадки
≤ `CANYON_RETURN_PAD_REACH`; отказы приходят текстом. Взято 6, а не 5 из плана: клиент предлагает `[E]` по
трёхмерному расстоянию в 5 метров, сервер считает по горизонтали — без метра запаса игрок в прыжке или на
камне получал бы отказ на кнопку, которая ему предложена. `runCleared` ставится при смерти босса сегмента,
сбрасывается в `preparePlayerEnemiesForSegment` и `enterCanyonHub`. Позиция площадки — общая формула:
сервер `canyonReturnPadPosition(segment)`, клиент `RETURN_PAD_OFFSET` в `canyonMath.ts`, оба дают
`startZ + 100 + 360 + 20`.

**Дисконнект.** В `ws.on('close')` перед `persistPlayer`: `isCombatLogout(player)` (жив и либо в боевом
режиме, либо в сегменте каньона) → `dropRunLoot(player)`, который сейчас просто чистит инвентарь. В Фазе 3
он же станет местом создания ящика — менять точку вызова не придётся.

### Отступления от плана

**1. Площадка эвакуации перенесена сразу (пункт 21 Фазы 4).** Серверная проверка расстояния и позиция
площадки на клиенте — одно и то же число. Оставить проверку в Фазе 1, а перенос в Фазе 4 означало бы, что
между ними каньон вообще не выпускает игрока: пад стоял на `startZ + 15`, проверка ждала его на
`startZ + 480`. Поэтому в `SegmentBuilderSystem` площадка строится погашенной (`emissiveIntensity` 0,
свет 0) и не регистрируется как интерактив; `ReturnPad.setActive(true)` зажигает её и добавляет в
интерактивы из `ProgressionSystem.applyBossDefeated`.

**2. Телепорт после `stuckTeleport` выполняет клиент, а не сервер.** В плане было «принудительный телепорт
через `spawnInSafeZone` + `notifyLocationTransition`». Так делать нельзя из-за порядка сообщений: клиентский
`changeLocation` чистит `lootSystem` / `enemySystem` / `buildSystem`, то есть стёр бы `lootState`,
`signState` и `enemyState`, отправленные сервером заранее. Во всей игре смена локации идёт от клиента
(`changeLocation` → `sendLocationChange` → `handleLocationChange`), и `respawnPlayer` устроен так же.
Поэтому сервер валидирует, тратит кулдаун и отвечает, а перенос делает клиент через
`applyStuckTeleport` → `placeAtLocationSpawn`. Эксплойта тут нет: и бой, и каньон отсекаются на сервере
до всякого перемещения, а игнорирование ответа не даёт читеру ничего — он просто остаётся на месте.

Побочно: точка приземления берётся из `getSpawnPoint()` локации, а не из серверных координат. У `main-world`
есть террейн, и серверный `spawnInSafeZone` отдаёт `y = 0` — по нему игрок мог бы оказаться под землёй.
Поле `position` из ответа поэтому убрано, клиенту едет только `locationId`.

### Найдено по дороге и починено

**Зачистка сегмента засчитывалась только в первом биоме.** В `applyEnemyDamage` условие было
`enemy.type === 'slime_boss'`, а боссы биомов разные (`husk_boss`, `frost_boss`, `spore_boss`, `void_boss`).
То есть со 2-го сегмента убийство босса не давало ни XP за зачистку, ни следующего сегмента, ни падения
ворот. Теперь при спавне запоминается `player.canyon.bossId` (как `player.cave.bossId` в пещере), и
проверка идёт по id. Без этого `runCleared` работал бы только в Slime Valley.

**`killerId: null` ронял обработчик смерти на клиенте.** `onPlayerDeath` делал
`data.killerId.startsWith('canyon-')` без проверки на null. Вынесено в `killerNameFor`, тип поля стал
`string | null`.

### Что проверить в игре именно по этой пачке

Пункты 1, 2, 3, 12, 13 из раздела 15 плюс:

### Четыре дыры, найденные при сверке, — исправлены

`applyPlayerStatus`. В деплое с одной игрой поведение и число запросов не меняются.

ящик — токены не терялись (их подхватывает `storageOrphan`), но защита из плана не работала. Снимок
теперь уходит при авторизации и при входе в свою комнату; UI такой снимок игнорирует (`state.key === null`),
редактор — берёт.

## 19. Фаза 3 — сделано 17.08.2026

Пункты 14–20 чеклиста. Лежит в рабочем дереве обоих репозиториев незакоммиченным.

### Как устроено

**Ящики живут в своей карте, а не в `lootDrops`.** План предлагал класть их туда же с полем
`kind: 'crate'`. Отказался: тогда крейт-осведомлёнными пришлось бы делать всех четырёх потребителей
`lootDrops` — `serializeLoot`, `clearCanyonLoot`, сборщик мусора и `handleLootPickup`, — и забытая
проверка в любом из них становится багом (например, `serializeLoot` разослал бы ящик как `lootSpawn` с
`tokens: undefined`). Отдельная `deathCrates` даёт пункт 16 чеклиста бесплатно: `clearCanyonLoot` и
`preparePlayerEnemiesForSegment` физически не видят ящиков.

**Видимость — одна функция `crateVisibleTo(crate, viewer)`,** через неё идут и снимок, и рассылка, и
проверка при подборе. Правила: та же локация и тот же шард; вне каньона видят все; в каньоне сравнивается
«зона» — хаб или номер сегмента, — а ящик в сегменте видит только владелец. Так закрыт риск «ящик виден в
чужом сегменте» и заодно тот, что в плане не назван: ящик из хаба не должен светиться игроку, который
ушёл на 1500 метров вглубь.

**Снимок `crateState`** уходит при авторизации, смене локации, входе в сегмент и возврате в хаб. Без него
забег за телом не работал бы: варп в сегмент не является сменой локации, и клиент никогда бы не узнал про
ящик. Снимок полный, клиент сверяет и убирает то, чего в нём нет.

**Что едет по проводу.** Наружу отдаётся `stacks` — число стеков, а не сами `entries`. Полный инвентарь
на 200 позиций весил бы десятки килобайт на каждую рассылку и показывал бы всем вокруг точный состав
чужой добычи. Серверная запись при этом хранит стеки целиком.

**Подбор.** `handleCrateLoot` синхронен от `deathCrates.get` до мутации — между проверкой и переносом нет
ни одного `await`, поэтому одновременное `E` двух игроков разруливается само: второй вызов уже не находит
запись. Что не влезло в 200 позиций инвентаря, остаётся в ящике, и он переизлучается с новым числом
стеков.

**Страховка** списывается первым шагом в `dropRunLoot`, до создания ящика, и только если инвентарь не
пуст — умирать пустым не тратит заряд. Приходит `insuranceConsumed`, клиент показывает «Insurance paid
out — your tokens are safe».

### Дыра, найденная в собственном коде

Списание страховки не сохранялось. Опрос `player-status` раз в 8 секунд сверяет `placeables` с базой и
перезаписывает их значением из БД; `economyChangedAt` прикрывает только 5 секунд, а ближайший автосейв —
через 30. То есть игрок терял заряд, а через восемь секунд получал его обратно бесплатно. Теперь
`dropRunLoot` заканчивается `persistPlayer`. Это же закрывает мелкий эксплойт с потерей инвентаря: без
сохранения падение сервера возвращало бы выброшенные токены.

### Сознательные отступления

- **Дисконнект в сегменте каньона создаёт ящик, который никто не увидит.** `player.id` выдаётся на
  соединение и при перезаходе меняется, так что владельцем этой записи уже никто не станет. Инвентарь при
  этом чистится — правило против combat log работает. Запись живёт пять минут и умирает в сборщике мусора;
  городить отдельную ветку ради неё не стал.
- **Арена в исключениях заранее.** `CRATE_BLOCKED_LOCATIONS` содержит `tower-events`, хотя самой арены
  ещё нет. Пункт 21 из решений («лут на арене не выпадает») выполнен до того, как появится, что можно
  забыть.
- **`handleLootPickup` не трогал.** План предлагал добавить туда `cave` ради ящиков, но у ящиков свой
  обработчик без белого списка локаций — они работают везде, кроме арены.

## 21. Фаза 5 — сделано 17.08.2026

Пункты 24 и 25 плюс отдельное требование владельца: **члены группы не наносят друг другу урон**.

### Группы

Новый модуль `game-server/party.js`, состояние только в памяти. Проверяется скриптом
`npm run check:party` (по образцу `check-abilities.js`) — 28 проверок на формирование, лимит, союзность,
кик, передачу лидерства, дисконнект и протухшие приглашения.

**Группа создаётся в момент принятия, а не приглашения.** В плане приглашение ссылалось на `partyId`, но
тогда пригласивший немедленно оказывается в «группе из одного», и если все откажутся — так в ней и висит.
Поэтому приглашение ссылается на **пригласившего** (`fromId`), а группа рождается при первом «принять».
Отсюда `partyAccept { fromId }` и `partyDecline { fromId }` вместо `partyId` из плана.

Правила: максимум 4; приглашать может любой участник, кикать — только лидер; лидер вышел — лидерство
уходит следующему; осталось меньше двух — группа распадается; приглашение живёт 60 секунд, протухшие
подчищает интервал и шлёт `partyInviteExpired`; дисконнект вычищает и членство, и все приглашения игрока
в обе стороны.

Приглашение уходит **по кошельку**, как у трейда (`walletToPlayer` на сервере), а не по сетевому id.
Так пункт «Invite to party» встал в существующее меню по клику на никнейм — оно работает в чате, в списке
друзей и в профилях, и ничего нового искать не нужно.

**Добавлено сверх плана: `partyVitals`.** Рамки участников без здоровья бесполезны, а `partyState`
с полным составом рассылать по каждому изменению HP — это десятки сообщений в секунду. Поэтому раз в
500 мс группам из двух и более уходит короткий пакет id/HP/жив/локация. Полный `partyState` шлётся только
при смене состава.

Клиент: `ui/hooks/usePartyState.ts`, `ui/PartyPanel.tsx` (вкладка Party в `SocialWindow`),
`ui/PartyInvitePopup.tsx` по образцу `TradeInvitePopup`, рамки участников под полосой XP в `HUD.tsx`.

### Урон по своим

Оказалось, что весь урон между игроками проходит ровно через две точки, и это сильно упростило дело:

- `canAbilityHitPlayer` — через него идут все способности, зоны, отложенные удары, рикошет, детонация
  взрывного патрона, контроль и выбор цели по прицелу (всё это построено на `forEachAbilityTargetPlayer`);
- `handleHit` — обычное попадание пулей.

В обе добавлена проверка `party.areAllies`. Лечение и баффы не задеты: они идут через отдельный
`forEachAbilityAlly`, который союзников как раз ищет.

**Третья точка нашлась на клиенте.** Замедление от вражеских зон (`slow_field`, `suppression_field`,
`time_dilation`) клиент накладывает сам себе — так было сделано в Фазе 6в, потому что движение игрока
клиентское. `hostileSlowAt` исключала только собственные зоны кастера, поэтому кольцо союзника продолжало
бы тормозить. Теперь в неё едет набор id членов группы, который `GameNetworkHandlers` обновляет из
`partyState`.

Осознанно не тронут толчок Whale Splash: урона у него нет, а отталкивание союзника — это мем, а не
дружественный огонь.

### Что проверить в игре

- приглашение через меню по никнейму приходит попапом, «Принять» собирает группу у обоих;
- вкладка Party показывает состав, корону лидера, HP и локацию; рамки участников видны в HUD слева;
- HP участника в рамке меняется, пока он в другой локации;
- выстрел в союзника не снимает здоровье, граната и зоны его не задевают, замедление от его зоны не липнет;

- кикнутый получает сообщение и перестаёт быть союзником (урон снова проходит).

кривую сложности, потолки наград и жизненный цикл забега.

### Изоляция забегов

**Один забег на инстанс `tower-events`, а не отдельный шард на каждый.** План говорил «изоляция через поле
`instance`», и это оно и есть, только с другой стороны: забег **ключуется** инстансом, а не переселяет в
него игроков. Причина — враги в игре и так рассылаются адресно (`safeSend` на игрока), поэтому посторонний
в зале просто не получает мобов забега и ничего не видит. Единственное, что физически одно на зал, — свеча,
поэтому второй забег в том же инстансе отклоняется с `instance_busy`, а игроки переключают шард
существующим переключателем. Так не понадобилось ни строчки новой машинерии переселения.

### Волны и ИИ

Враги забега — **общий набор на всю группу**, в отличие от каньона, где набор на игрока. Из-за этого у
арены свой тик (`arenaTick`, те же 100 мс), который обходит забеги, а не игроков.

`arena.js` держит чистую часть: реестр забегов, фазы `prep` / `wave` / `pause` / `over`, состав волны,
кривую сложности и арифметику наград. Таблицы мобов ему не нужны — он возвращает `biomeIndex`, а
`server.js` уже достаёт из `CANYON_BIOMES` конкретных моба и босса. Так не пришлось ни дублировать
таблицы, ни тянуть их в модуль.

Состав: биом сменяется каждые 5 волн и упирается в Void Rift, каждая 5-я волна — босс биома плюс свита,
число мобов растёт с волной и упирается в потолок 30 одновременно. Здоровье и урон растут каждую волну.

**Свеча как цель.** Пункт 27 оказался дешевле, чем ждал план: трогать пять мест движения врагов не
пришлось, потому что арена не переиспользует канйонный цикл, а имеет свой `moveArenaEnemy`. Правило одно:
ближайший стоящий на ногах участник в радиусе агро — цель; никого нет — идём к свече и бьём её.
Павшие из выбора цели исключены, поэтому мобы не топчутся над телами.

### Смерть, подъём и выход

Смерть на арене ничего не отнимает — `dropRunLoot` возвращает `kept` (это чинилось в Фазе 4), а сам игрок
помечается павшим и остаётся лежать там, где упал. Подъём — интеракция по `E` на теле союзника, канал 3
секунды, **только в паузе между волнами**; тело регистрируется как интерактив ровно на время паузы, так что
вне её подсказка не появляется. Урон по поднимающему обрывает канал. Поднятый встаёт с половиной здоровья.

Нажать «возродиться» на экране смерти можно всегда — это и есть выход из забега: игрок покидает состав,
получает кулдаун и уходит в выбранную точку.

Забег кончается, когда свеча на нуле или на ногах никого не осталось.

### Награды

`ash = 25 × зачищенных волн`, потолок 1500; `xp = 50 × зачищенных волн`, потолок 3000. Оба потолка
приходятся ровно на 60-ю волну — это и подтвердило, что в плане имелась в виду выплата **от достигнутой
волны**, а не сумма по всем волнам (сумма упёрлась бы в потолок уже к 11-й). Начисление одно, в конце.

**За мобов арены XP не капает.** `grantEnemyKillXp` для арены пропущен: иначе рядом с ограниченной
наградой за забег появился бы второй, неограниченный источник, и потолок в 3000 ничего бы не значил.
Квесты на убийства и `healOnKill` / `energyOnKill` работают как обычно — это боевые механики, а не доход.

Кулдаун час и лучший результат живут в `progress.data.arenaCooldownUntil` и `arenaBestWave`.

### Клиент

`EventsHall` получил свечу в центре (растёт с волной, зеленеет-краснеет по здоровью, вспыхивает от удара),
четыре арки спавна по сторонам и терминал запуска. **Лифт-кристалл сдвинут в угол** — он стоял ровно в
центре, где теперь свеча; не заметить это было бы дорого, потому что кристалл — единственный выход с этажа.

Новые `ui/ArenaPanel.tsx` (правила, старт, кулдаун, итоги забега), `ui/ArenaHUD.tsx` (волна, HP свечи,
таймер паузы, состояние товарищей), `ui/hooks/useArenaState.ts`.

### Что проверить в игре

- терминал в зале открывает панель, «Light the candle» стартует забег через 5 секунд подготовки;
- мобы идут из арок; если отойти от свечи и спрятаться, они переключаются на свечу и сбивают ей HP;
- каждая пятая волна приносит босса;
- павшего товарища видно в HUD как DOWN, подсказка подъёма появляется **только** в паузе;
- поднятый встаёт с половиной здоровья, урон по поднимающему обрывает канал;
- смерть на арене не роняет ящик и не тратит страховку;
- забег кончается, приходит одна выплата, кулдаун виден в панели и переживает перезаход;
- второй забег в том же зале отклоняется с понятным текстом, на другом шарде запускается;
- в консоли сервера нет строк `[!] ... hack:` при стрельбе по мобам арены.

## 23. Счётчик онлайна — правка 17.08.2026

Не из плана, отдельная жалоба: счётчик не показывал игроков из других локаций.

Причина — два писателя в одно поле. Сервер шлёт `count` со всеми авторизованными игроками и рассылает его
всем, независимо от локации; это работало верно. Но клиентский `updateOnlineCount` записывал в то же
`hudState.online` число **видимых** игроков (`otherPlayers`, у кого не выставлен `isHidden`), и вызывался
он при каждом входе-выходе игрока из зоны видимости — то есть почти всегда затирал серверное число
локальным.

Присвоение убрано, счётчик теперь берётся только из `count`. Метод переименован в `syncNearbyPeers`,
потому что после правки он делает ровно одно — синхронизирует пиров голосового чата по видимым игрокам;
`emitState` оттуда тоже убран, менять в HUD ему больше нечего.

`broadcastCount` на сервере вызывается в конце `handleAuth` и в `ws.on('close')` — этим покрыты оба
события, меняющие число авторизованных, так что отдельного тика счётчику не нужно.
